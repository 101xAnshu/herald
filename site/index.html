Herald is an open-source notification system built on a transactional outbox. One commit writes the event, its timeline, and the outbox. Then every delivery is tracked to a terminal state. 29,989 events in, zero lost.

How it works

One promise,
three mechanisms.

Each mechanism exists for one reason: a notification must never silently disappear.

01 / Commit

Accept first.
Decide later.

The event, its timeline, and the intent to publish commit in a single Postgres statement. Your API returns 202 only after the work is durable.

  • One SQL statement, three writes
  • 202 after the commit, never before
  • The outbox is the recovery plan

Scope

Limits,
written down.

Herald is a local demo shaped like production, not production itself. What is missing is listed here, not hidden.

Read the capacity model →
One Postgres shard, one Kafka broker, one Redis

The demo keeps the dependency footprint small. It is not a claim about a multi-region deployment.

Push and SMS are deterministic mocks

Email goes to Mailpit. Push and SMS return scripted outcomes so the failure path is reproducible.

300M events/day is a design target, not a measurement

The measured ceiling is 4.3M events/day on the 4-core laptop used for the runs.

Local tables are not partitioned

Retention deletes in batches. Partitioning is the first change for a larger deployment.
